# Log de defectos introducidos

Una fila por defecto que **yo introduje** (no por bug heredado ni por hallazgo de auditoría
sobre código viejo). Existe para que "¿estamos mejorando?" deje de ser una sensación.

Nació el 2026-08-04, cuando Favio observó que seguían apareciendo errores pese al cambio de
modelo, y quedó claro que el problema no era el modelo: había **siete memorias** de feedback
diciendo variantes de "verificar mejor" y una de ellas se violó al día siguiente de escribirla.
Una memoria no es un control. Un control es algo que corre y falla.

## Cómo se usa

- **Una fila por defecto**, el día que se descubre. Incluye los que se encuentran y arreglan en
  la misma sesión: esos son justamente los que enseñan barato.
- **La columna que importa es "clase"**, no la severidad. Si una clase se repite, falta un
  control mecánico, no disciplina.
- **"Lo encontró"** distingue lo que se atrapó solo de lo que se atrapó de casualidad. Si la
  mayoría dice "Favio" o "revisión posterior", la verificación previa no está funcionando.
- El retro semanal (`/retro`) lo lee. Sin esto, cada sesión empieza creyendo que la anterior
  fue limpia.

## Clases vistas hasta ahora

| Clase | Qué la produce |
|---|---|
| `camino-feliz-unico` | verifiqué lo que construí, no la rama de error / el usuario del muro / el kill duro |
| `efecto-lateral-al-deduplicar` | unifiqué dos caminos que *decían* lo mismo sin mirar qué *hacían* además |
| `consumidor-no-actualizado` | agregué estado nuevo y no actualicé a todos los que lo leen o lo copian |
| `error-no-leido` | supabase-js no lanza; sin leer `{error}` un fallo se lee como "no había nada" |
| `barrido-de-un-solo-arbol` | escribí el guard que cierra un hallazgo mirando solo el repo donde lo encontré, cuando el mismo hallazgo vive en los dos canales |
| `antivacuidad-anclada-al-defecto` | el control anti-vacuidad se apoya en que el problema siga existiendo, así que arreglarlo rompe el build |
| `cobertura-alrededor-del-cambio` | los tests que escribí junto al fix cubren todo menos el cambio de comportamiento en sí; revertirlo los deja verdes |
| `barrido-ciego-por-preprocesado` | el paso que limpia el fuente antes de barrerlo borra justo el texto que había que mirar |
| `asercion-vacua-por-implicacion` | la aserción tiene forma `if (P) expect(Q)`, así que si P deja de cumplirse el test pasa sin comprobar nada |
| `causa-inventada-junto-al-numero` | el número es real y verificable, la explicación que va al lado no se midió; corregir el número deja la causa falsa intacta y se propaga en copias |
| `guard-limitado-al-corpus-existente` | el guard compara dos implementaciones sobre lo que HAY en el árbol, así que una divergencia sobre una ruta que todavía no tiene archivos es invisible |
| `correccion-que-abre-la-direccion-opuesta` | al arreglar un falso negativo ensanché la condición y abrí un falso positivo; el caso original queda cubierto y la prueba por mutación solo mira ese lado |
| `paridad-entre-proyecciones` | el guard compara dos copias por una PROYECCIÓN (un conjunto, un veredicto sobre lo que existe) en vez de por lo que son; por cada proyección hay mutaciones que no la cruzan, así que taparle una deja las otras |
| `evidencia-que-no-discrimina` | la observación es real y se cita como prueba, pero es igual de compatible con la hipótesis contraria: no separa las dos, solo no las contradice |
| `cobertura-que-cuenta-lo-que-no-verifica` | la métrica de cobertura cuenta apariciones en vez de casos DECISIVOS, así que informa un número alto justo donde no se probó nada |
| `guard-partido-por-una-extraccion` | partí una función en dos y el guard que la miraba quedó cubriendo una mitad; la misma mutación que ya se había verificado pasa de nuevo, un nivel más abajo |
| `equivalencia-verde-por-casualidad` | el test declara que dos implementaciones son equivalentes y no lo son; queda verde porque ningún caso de prueba toca la diferencia, y todo lo que se apoye en esa equivalencia hereda el hueco |
